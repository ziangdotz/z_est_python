## 2. 测量条件（复现前必读）

- **样本**：`8ckup/NIST_SP800-90B_EntropyAssessment/bin/truerand_4bit.bin`
  （1,000,000 字节；`len=1000000`、`blen=4000000`、`alph_size=16`）。
- **机器**：i7-11800H，8 物理核 / 16 逻辑，16 GiB 级内存；`numba 0.67.0` + `llvmlite 0.49.0` + `numpy 2.2.6`。
- **本机持续负载会降频**：热态整体约 ×1.3。本次多轮测量都偏热，所以
  `-j 1` 实测 34.9 s 对文档冷态基线 30.4 s。**只有同一轮内的比值可信**；
  判定改动是否有效要拿等价性证据（§5），不要拿耗时数字。
- **内存读数手法**：环境里**没有 `psutil`**，用 ctypes 调 `kernel32!K32GetProcessMemoryInfo`。
  ⚠️ 必须显式设 `GetCurrentProcess.restype = HANDLE`，否则 64 位下句柄被截断成 `c_int`，
  函数返回 0 而报「调用失败」（本次第一版就踩了这个）。跨进程总量用 PowerShell 轮询
  `Get-Process python | Measure WorkingSet64 -Sum` 取最大值。代码见附录 A。
- 本次探针脚本（`_tmp_res_probe.py` / `_tmp_res_run.ps1` / `_tmp_numba_cost.py`）已按仓库规则删除，
  内容全部收录在附录 A。

## 3. 当前基线（全部实测）

### 3.1 端到端

| 运行 | 墙钟 | 峰值内存（所有 python 进程求和） | CPU 时间 | 进程数峰值 |
|---|---|---|---|---|
| `ea_non_iid -j 1` | 34.9 s（冷态基线 30.4 s） | **598 MiB** | 34.4 s | 1 |
| `ea_non_iid -j 8` | 21.8 s（冷态基线 16.9 s） | **1,629 MiB** | 61.2 s | 9 |
| `ea_iid`（默认并行） | **44.8 s** | 未单列 | — | — |

> IID 路径比非 IID 还慢，这个事实此前没被量化过；见 §4-A3。

### 3.2 单进程内逐 job 内存增量

峰值单调，故用「调用前后 peak 之差」当作该 job 的增量峰值。

| job / 视图 | 峰值增量 | 归因 |
|---|---|---|
| **tTupleLRS / Bitstring** | **+419.8 MiB** | 全仓最大内存户，同时也是最贵 job |
| **MultiMMC / Literal** | **+124.0 MiB** | 16 阶上下文的 `dict` |
| Compression / Bitstring | +28.0 MiB | bz2 一次性压缩 |
| Markov / Bitstring | +2.9 MiB | — |
| Collision / Lag / MultiMCW / LZ78Y（两视图） | ≈ 0.0 MiB | — |
| 单进程跑完整轮之后的总 peak | **619.6 MiB** | — |

### 3.3 `sa_algs` 内部拆分（本次最重要的新发现）

热态下 `tTupleLRS/Bitstring` = 17.01 s，拆开是：

| 阶段 | 耗时 | 占比 | 换算到冷态 11.8 s 基线 |
|---|---|---|---|
| `build_suffix_array`（numpy 前缀倍增） | 2.33 s | 13% | ≈ 1.6 s |
| `sa_to_lcp`（**列表化 Kasai，Python 循环**） | 5.20 s | 31% | ≈ 3.6 s |
| Kaufer 扫描（`S`/`A` 累加，Python 循环） | 9.48 s | 56% | ≈ 6.6 s |

原先文档写「Kaufer 扫描 11.8 s」是把整个 job 都记在它头上了。**实际有两块 Python 循环**，
应当一起做：njit 之后该 job 只剩 SA 的 ≈ 1.6 s。

规模与数组预算：

| 量 | 实测 |
|---|---|
| n（位串样本） | 4,000,000 |
| SA / LCP | 各 30.5 MiB，`int64` |
| **v（LCP 最大值）** | **42** |
| `L = sa_to_lcp(...).tolist()` 的代价（估算） | 指针 8 B × 4M = 30.5 MiB，加小整数对象 28 B × 4M = 106.8 MiB，**≈ 137 MiB** |
| njit 版 `S`/`A` 用 int64 | 2 × (v+2) = 2 × 44 槽 ≈ **0.3 KiB**；最坏 v=n 时 32 MiB |

int64 不溢出的证据（原文档只做了理论推算，这次补上实测规模）：v=42、n=4M，
`(n−i)(n−i+1)/2 ≈ 8e12`，`S[i]` 的上界同量级，距 int64 上限 9.2e18 有 6 个数量级余量。
32M 样本时 ≈ 5.1e14，仍安全。

### 3.4 固定成本与依赖体积

| 项 | 实测 |
|---|---|
| numba 安装体积 | 20.1 MiB / 1,545 文件 |
| llvmlite 安装体积 | **115.8 MiB** / 77 文件（可选依赖的绝大部分成本在这里） |
| numpy | 24.0 MiB |
| tensorflow / keras / mpmath | 1,394 MiB / 9 MiB / 3 MiB（**已装，但重写版完全没引用**） |
| 整个 conda 环境 `site-packages` | 1,881 MiB |
| JIT 磁盘缓存现状 | `ea/__pycache__` 现 64 文件共 1,123,002 B（46 个 `.pyc` + 18 个 JIT 缓存）；其中 `.nbi/.nbc` 18 文件 801,614 B ≈ **783 KiB**，8 个 kernel ⇒ **≈ 98 KiB / kernel**。⚠️ 这是个会漂的快照：`.nbc` 数（10）多于 `.nbi`（8），因为同一 kernel 按不同签名各特化一份，跑过新形状的输入就会再多一份。2026-09-04 那轮读数是 10 文件 468,049 B。做 A1/A2/A3 时按「每新增一个 kernel ≈ +100 KiB，每个新签名再 +几十 KiB」估即可 |
| `import numba` 冷启动 | **0.32 s**，RSS 13 → 56 MiB（+43 MiB），**commit charge 520 MiB** |
| 单个 4M 元素极简 kernel 冷编译 | ≈ **0.50 s**（1024 元素版 103 ms）；缓存命中后 0 |

> commit charge 520 MiB/进程 是 `-j > 6` 反而回升的机理解释：8 个 worker 各导一次 numba，
> 就是 4 GiB 量级的 commit。任何「让 worker 也去 import numba」的改动都要付这笔账。

## 4. 候选项详情

### A1 `sa_algs` 的 Kaufer 扫描 + Kasai LCP 上 njit —— **推荐首做**

- **现状**：位串视图整个 job 冷态 11.8 s / 热态 17.01 s，其中 Kaufer ≈ 56%、Kasai ≈ 31%、SA ≈ 13%。
  单进程峰值内存 +419.8 MiB，也是最大户。
- **改法**：沿用已确立的三件套（见 `ea/_jit.py` 与既有四个预测器）——
  `_kaufer_counts()` 纯 Python 权威版 + `@Kernel _kaufer_kernel()` + 入口 `if use_jit(length)` 分派；
  `sa_to_lcp` 同法。**关键配套改动**：`L` 不再 `.tolist()`，直接把 int64 ndarray 喂进 kernel
  （这既是 njit 的前提，也是省 137 MiB 的来源）。注意参考实现的口径：`del L[0]; L.append(0)`，
  njit 版要保持同一份偏移，否则逐行输出会变。
- **编码耗时**：约 130 行改动 + 2 个 `jit_crosscheck` 用例，**30–45 min**。
- **回归机器时间**：**15–20 min/轮 × 2–3 轮**（`refdata_diff --all` 估算 8–12 min，主要花在
  biased-random-bytes 单样本约 209 s）。
- **预计收益**：位串 job 11.8 → **约 1.7–2.0 s**；`-j 1` → **约 21 s**；`-j 8` → **约 11 s**（瓶颈换成 MultiMMC/符号 8.4 s）。均为估算。
- **资源变化**：该 job 峰值 420 → **约 280 MiB**；`-j 1` 全程 598 → 约 460 MiB；`-j 8` 1,629 → 约 1,200–1,300 MiB。
  新增磁盘：2 个 kernel 的 `.nbi/.nbc` 约 **+200–300 KiB**；一次性冷编译 +1–2 s，缓存命中后 0。
- **风险**：低。这是四段已验证过的套路，且 `lrs_bench.py` 有 SA/LCP/sa_algs 的中间量指纹可比对。

> ⚠️ **收益范围有一条硬限制（2026-09-28 补记，A1/A2/A3 三条 njit 项全适用）**：
> 桌面应用的 Nuitka 打包在 `est_test_x_vue3_pywebview/Makefile:97-98` 传了
> `--nofollow-import-to=tensorflow,keras,markov_chain_generate,numba,llvmlite`
> 与 `--noinclude-numba-mode=nofollow`，所以**打包出的 exe 里 njit 永远不会启用**
> （`ea/_jit.py` 的分派会一路走纯 Python 权威版）。
> 上面那些「11.8 → 1.7–2.0 s」「`-j 8` → 约 11 s」的数字**只落在 CLI 与 FastAPI 两种部署上**。
> 若目标是给桌面端提速，A1 不是答案——要么改打包配置把 numba 纳进来
> （代价：onefile 体积与冷启动，且 `frozen()` 守卫那条路径从未被验证过），
> 要么去做不依赖 numba 的向量化（E3 那一档）。

### A2 通用字母表的 MultiMMC / LZ78Y 上 njit

- **现状**：符号视图冷态 8.4 s / 5.3 s（本次热态实测 11.60 s / 7.74 s）；MultiMMC/符号 dict **+124 MiB**。
- **难点（已量化）**：1M 符号 × 16 阶上下文 → 字典条目 ~10⁶ 量级。要先把它换成 njit 能吃的
  开放寻址表（int64 key + int32 count，负载因子 0.5 ≈ 2M 槽 ≈ 24–30 MiB），
  并**逐字复现 `predict()` 的平局规则**——这是唯一会改变输出数字的地方，必须靠
  `jit_crosscheck` 直接比原始计数。
- **编码耗时**：250–400 行，**2–4 h**；回归 **20–30 min**。
- **预计收益**：`-j 1` 约 21 → 17 s，`-j 8` 约 11 → 8–9 s。总收益 < 12 s。
- **资源变化**：内存**下降 4–5 倍**（124 → 24–30 MiB），磁盘 +300 KiB 量级。
- **风险**：**最高**。上一轮已明确否决过一次（「收益 < 12 s 而风险最高」）。
  **重开条件**：A1 完成后它成为第一瓶颈，且愿意先给 `jit_crosscheck` 补一个覆盖平局路径的用例。

### A3 `permutation.py` 的碰撞检验上 njit —— **位置需要纠正**

- **事实更正**：实测确认 `permutation_tests` **只被 `ea/iid_pipeline.py` 调用**，
  它不在非 IID 那 30.4 s 里，而在 IID 路径的 **44.8 s** 里。文档里把它挂在非 IID 性能清单下是错的。
- **收益上限**：44.8 → **约 30–35 s**（按「非二进制样本上占单轮 32%」折算，属估算）。
- **前置缺口**：`refdata_diff.py` 只比对 `ea_non_iid -vv`，**IID 侧没有端到端验收工具**。
  动 A3 之前要先补一个 IID 版 refdata 比对（C++ 的 `iid_main` 有 selftest 基准可用），约 30–60 min。
- **资源代价 ⚠️**：置换检验按轮次开 8 worker，njit 化会让**每个 worker 各导一次 numba**：
  每进程 +43 MiB RSS / **+520 MiB commit**，8 进程约多 **4 GiB commit**。这是内存**负收益**项，
  可能重演 `-j > 6` 的回升。落地时必须配一个「worker 内是否禁用 JIT」的开关来验证这点。
- **编码耗时**：80–150 行，**45–90 min**，不含前置工具。

### A4 `libdivsufsort` ctypes 封装 —— 建议长期挂账不做

SA 实测只占 1.5 s（冷）/ 2.33 s（热），收益 ≤ 1.5 s；代价是 Windows 上要自行编译 `.dll`
（+200–400 KiB）、维护 ctypes ABI、Nuitka 打包链路要额外携带二进制。**不划算。**

### B 规范化 C 档（上轮按你的选择跳过，此处登记）

1. `pyproject.toml` 包化 + 干掉 **14 处 `sys.path.insert`**（分布在 14 个文件）：编码 **1.5–2 h**
   + 全入口手工回归 20 min；运行时无资源变化，多一个 `.egg-info`。
2. 路径机制内部不一致：`refdata_diff.py` 用 `Path(__file__).resolve().parents[1]`，
   而 `jit_crosscheck` / `job_bench` / `lrs_bench` 用 `sys.path.insert`。做第 1 项时顺手统一。
3. `8ckup/` 改名：tracked 内引用实测 **12 处**，约 20 min。
4. `est_core/` 无 `__init__.py`（与重写版风格不统一）。

### C 功能缺口

- **DNN 预测器（FC / RNN）从 `est_core` 移植到重写版**：磁盘**零增量**——
  `tensorflow==2.21.0` + `keras==3.12.2` 已在 requirements 且已安装（1,394 MiB），重写版一行都没引用。
  但运行时每进程 RSS **+300–600 MiB**、导入 **+2–4 s**，所以**只应挂在独立入口**
  （`main_dnn` 的对等物），绝不能进 `ea_non_iid` 主路径。编码 **3–5 h**。
- 流式 / 分块处理超大文件（现在全量加载，`-j 8` 的 1.6 GiB 峰值主要来自每个 worker 各持一份样本）。
- 结果可视化。

### E3 低成本向量化（recode 版，无需 numba）—— 部分落地，两条已否掉

这些都是**一次性的 O(n) 纯 Python 循环**，用 `np.bincount` / numpy 索引就能替掉。与 A3 的关键差别：
**不引入 numba**，所以不付每 worker 520 MiB commit 那笔账。量级上每项约 0.3–1.5 s（1M 样本），

E3-9 要特别说明**为什么没有照原计划用 `np.flatnonzero(data[:-1]==data[1:])` 全向量化**：
这个循环是 `i += t_v`（`t_v` 取 2 或 3）的**跳跃过程**，下一个访问位置依赖上一步的落点，
所以「所有相邻对里哪些相等」这个集合**推不出**实际访问到的位置序列。全向量化会算错。
能做的是把每步的成本从「两次 numpy 标量装箱 + `int()`」压到「一次 Python list 索引」，
并把 `sum_t += t_v; sum_t2 += t_v*t_v` 摊平成常量分支（`+2/+4.0` 与 `+3/+9.0`，
数值与 `t_v*t_v` 精确相等）。实测 8M 位串视图 **0.824 s → 0.281 s（2.9×）**。

探针还抓到一处我自己引入的回归：`d[:length-1]` 在 `length ≤ 1` 时负索引会**回绕**
（`length=0` ⇒ `d[:-1]` 取到几乎整个数组，与 `d[1:0]` 形状不匹配而抛 ValueError），
而原来的 `while i < length - 1` 对 `length ≤ 1` 是直接不进循环的。已用
`pairs = max(length - 1, 0)` 修掉。**这就是函数级探针比端到端更强的地方**：
端到端永远不会喂 `length=0`，这类边界只能靠构造用例踩出来。

另一处顺带查清的既有洞（**未修**，已登记为 **E1-13**）：`v == 1` 时
`collision.py:43` 的 `sigma_hat` 会 `ZeroDivisionError`——`v == 0` 有守卫，`v == 1` 没有。
HEAD 与改后**行为一致**（都抛同一个异常），所以不是本轮引入的；记在这里免得下次当成回归。

### E7 「向量化是否等价」的判据（2026-09-28 实测得出，E3-1 / E3-8 因此否掉）

写 E3 那一节时我假设「换成 `np.bincount` 就是精确等价」，**这个假设只对整数计数成立**。
实测把 E3-1 的靶子 `calc_proportions` 换成 `np.bincount(data)/n` 后，基线探针立刻显形：
`0.49919999999996134` 而不是 `0.4992`。原因是它逐样本累加 `1.0/n`（忠实复现 C++ 的写法），
而 `count/n` 是**一次除法**，两者的舍入误差不同。偏差随样本量增长：

| n | 与逐样本累加的差（绝对 / 相对） |
|---|---|
| 1e4 | -3.864e-14 |
| 1e6 | -6.436e-12 |
| 4e6 | **-1.854e-11 / 3.707e-11** |

1e-11 远超 §5 的 1e-9 严格档吗？不远，但它**已经落在「不是逐字相同」的区间里**，而本工程的
验收口径是「改动后必须逐字相同，否则就是改错了」。所以：

- **E3-1 否掉**。`calc_proportions` 的逐样本累加**不是低效写法，是等价性要求**。
  它喂给 `chi_square.py:299,351` 和 `_lrs.py:256`，改它会同时挪动卡方与 LRS 的输出。
  要提速只能上 njit 复现同样的累加顺序（属 A1 档，不是「低成本」）。
- **E3-8 否掉**。`_calc_T` 里的 `o.tolist()` 看着像多余转换，但它决定了 `T += (o-e)**2/e`
  的**求和顺序**；换成 numpy 数组运算是整块向量化，浮点加法顺序变了，结果就不再逐字相同。
  E3-2/3/4 落地时**刻意保留了 `_calc_T(bin_expectations, o.tolist())` 这个调用形式**，就是这个原因。

**可复用的判据**（下次评估向量化候选时先过这一关）：

1. 循环累加的是**整数计数** ⇒ `np.bincount` / 整数索引精确等价，可以做。
2. 循环累加的是**浮点**，且各项是 2 的幂或小整数（如 `4.0`、`9.0`）、总和 ≪ 2^53
   ⇒ 求和顺序无关，可以做（E3-9 的 `sum_t2` 属此类：项只有 4.0/9.0，实测总和 3250135.0
   在正序 / `np.sum` / 逆序下完全相同，上限 4.5e6 ≪ 2^53）。
3. 循环累加的是**浮点**，且项是 `1.0/n` 这类非精确值 ⇒ **不可以**换序，除非同时上 njit
   并逐字复现累加顺序。

## 6. 决策记录

- **A1 优先**：唯一同时满足「关键路径、内存下降、沿用已验证套路」的项。
- **A2 挂起**：收益 < 12 s 而风险最高，且要重写平局规则；只有 A1 之后成为第一瓶颈才重开。
- **A3 拆成两步**：先补 IID 的 refdata 比对工具，再谈 njit；且它是内存负收益，必须先量 commit。
- **A4 否决**：1.5 s 的收益换不回一个自编 dll 的维护成本。
- **DNN 不进主路径**：磁盘虽然零增量，但运行时 +300–600 MiB/进程、导入 +2–4 s，
  会破坏「小文件秒级出结果」的现有体验。
- **测量纪律**：耗时一律写区间；单次差异 < 10% 不下结论；判定改动有效只看等价性证据。

### A-1 进程内 RSS / 峰值（ctypes，无需 psutil）

```python
import ctypes, ctypes.wintypes

class PMC(ctypes.Structure):
    _fields_ = [
        ("cb", ctypes.wintypes.DWORD),
        ("PageFaultCount", ctypes.wintypes.DWORD),
        ("PeakWorkingSetSize", ctypes.c_size_t),
        ("WorkingSetSize", ctypes.c_size_t),
        ("QuotaPeakPagedPoolUsage", ctypes.c_size_t),
        ("QuotaPagedPoolUsage", ctypes.c_size_t),
        ("QuotaPeakNonPagedPoolUsage", ctypes.c_size_t),
        ("QuotaNonPagedPoolUsage", ctypes.c_size_t),
        ("PagefileUsage", ctypes.c_size_t),
        ("PeakPagefileUsage", ctypes.c_size_t),
    ]

_k32 = ctypes.windll.kernel32
_f = _k32.K32GetProcessMemoryInfo
_f.argtypes = [ctypes.wintypes.HANDLE, ctypes.POINTER(PMC), ctypes.wintypes.DWORD]
_f.restype = ctypes.wintypes.BOOL
_k32.GetCurrentProcess.restype = ctypes.wintypes.HANDLE   # ← 不设这行就会假失败

def rss():
    c = PMC(); c.cb = ctypes.sizeof(c)
    if not _f(_k32.GetCurrentProcess(), ctypes.byref(c), c.cb):
        raise OSError("GetProcessMemoryInfo failed")
    return c.WorkingSetSize / 1048576.0, c.PeakWorkingSetSize / 1048576.0  # MiB
```

逐 job 用法：`gc.collect()` → 记 `base = rss()[1]` → 跑估计器 → `rss()[1] - base` 即该 job 的增量峰值。

### A-5 oracle 对拍探针（改动前的小函数，整段抄进探针当参照）

**适用**：函数体不长、且**端到端喂不到边界输入**的情况（如 `collision_test` 的 `length = 0/1/2`、
`v == 1`）。比 A-4 强的地方：不用「改前跑一次、改后跑一次」两轮，**一次运行就出结论**，
还能顺手构造真实样本永远碰不到的边界。

做法：`git show HEAD:<path>` 取出旧实现，把函数体**逐字抄进探针**改名 `xxx_orig`，
同一份数据两边各算一遍比 `repr()`。关键点：

```python
def check(name, data, length):
    """比返回值；两边都抛异常时比异常类型——原始实现 v==1 时会 ZeroDivisionError，
    那是它本来就有的洞，新旧一致就算等价。"""
    try:    a = repr(fn_orig(data, length))
    except Exception as exc: a = f"raise {type(exc).__name__}"
    try:    b = repr(fn_new(data, length))
    except Exception as exc: b = f"raise {type(exc).__name__}"
    assert a == b, f"{name}: orig={a} new={b}"
```

**必须把异常也纳入比对**，否则旧实现本来就崩的边界（`collision.py:43` 在 `v == 1` 时
`ZeroDivisionError`）会让探针自己崩掉，掩盖真正想测的东西。

用例要覆盖：真实样本 × 两个视图、把 `length` 截断到 `0..8 / 100 / 1001`（踩遍
`i < length-1` 与 `i < length-2` 两个分支）、全 0 / 全 1 / 全交替、
以及若干 `(n, 偏置概率)` 组合的随机串、外加一条 1e6 的长游程。本轮 216 组用例 0 处不符。

> **这个探针抓到了我自己引入的回归**：`d[:length-1]` 在 `length ≤ 1` 时负索引会**回绕**
> （`length=0` ⇒ `d[:-1]` 取到几乎整个数组，与 `d[1:0]` 形状不匹配抛 ValueError），
> 而原来的 `while i < length - 1` 对 `length ≤ 1` 是直接不进循环的。修法是
> `pairs = max(length - 1, 0)`。**端到端验收永远喂不到 `length=0`，这类边界只能靠构造用例踩出来。**

### A-8 E1-4 的三方对拍：HEAD vs 改后 vs recode

E1-4 的验收需要**三方**同时在场：HEAD（证明原先确实错）、改后（证明修好了）、

```python
import sys, math, importlib.util

sys.path.insert(0, "est_core_nist_cpp_recode")

    m = importlib.util.module_from_spec(spec); spec.loader.exec_module(m); return m

        old = OLD.theMostCommonValueEstimate(seq)[1]
        new = NEW.theMostCommonValueEstimate(seq)[1]
```

边界那一半用 oracle：把改动后的公式**独立重抄一遍**（不 import 被测模块），
随机 4000 组 `n∈[2,40)`、`k∈[2,7)` 逐个比 `pu` 与熵的**精确相等**，
再补 5 组常值序列专门验 `pu==1 ⇒ 熵==-0.0` 的符号位：

```python
def oracle(seq):
    from collections import Counter
    c = Counter(seq); L = float(len(seq))
    pmax = c.most_common(1)[0][1] / L
    pu = min(1.0, pmax + ZALPHA*math.sqrt(pmax*(1.0-pmax)/(L-1.0)))
    return pu, -math.log2(pu)
# ... 比较时用 got[0] != exp[0] or got[1] != exp[1]，常值序列另加
#     math.copysign(1, got[1]) != math.copysign(1, exp[1])   # -0.0 == 0.0 为真，必须比符号
```

两个坑：

- **`/tmp` 不是 Windows 原生 Python 能懂的路径**。Git Bash 的 `/tmp` 实际是
  `C:/Users/<you>/AppData/Local/Temp`（`pwd -W` 或 `cygpath -w /tmp` 可查），
  但传给 Windows 版 Python 的 `"/tmp/..."` 会被解析成**当前盘符根下的 `C:\tmp`**，
  报 `FileNotFoundError`。探针里的路径一律写 Windows 绝对路径。（A-6 也踩过一次。）
- **`-0.0 == 0.0` 在 Python 里是 `True`**，所以常值序列那条用 `==` 是**验不出符号差异**的，
  必须额外比 `math.copysign`。这一条是主动加的，不是踩出来的——`min(1, ubound)` 在
  `ubound > 1` 时返回的是 **int `1`** 而非 float，`-math.log2(1)` 得 `-0.0`，
  万一哪天有人把 `min(1, ...)` 改成 `min(1.0, ...)`，`==` 对比会一路绿灯。
